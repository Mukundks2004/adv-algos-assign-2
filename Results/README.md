## Methodology (for report section 3)

**Machine.**
- Hardware: Intel Core i9-13900H laptop (6 performance + 8 efficiency cores, 20 threads), 64 GB RAM, on mains power.
- Host: Windows 11 Pro, "Balanced" power plan.
- Benchmark environment: Ubuntu 22.04.5 in a Docker Desktop container (WSL2 kernel 6.18), gcc 11.4.0 `-O2 -std=gnu99`, GMP 6.2.1.

**What a single measurement is.** One `Benchmark` process for one (algorithm, size, repeat). The harness:
- allocates and touches every buffer, and calls the algorithm's setup;
- warms up 3 times;
- verifies the result against `mpn_mul_n`, exiting on any mismatch;
- times a loop with `clock_gettime(CLOCK_MONOTONIC)`, auto-calibrating the iteration count so the loop runs about 0.25 s;
- reports total time / iterations.

From 12,288 limbs for schoolbook, 49,152 for FFT and 65,536 for Karatsuba, one iteration already exceeds 0.25 s, so those points are single-shot timings.

**Fairness.**
- **Same inputs:** the seed is the repeat number, so at a given size and repeat every algorithm multiplies the same operands.
- **Interleaving:** algorithms run one after another for each size, and the repeat loop is outermost, so drift in machine state hits all algorithms alike.
- **Same building blocks:** all implementations use the same 64-bit radix and the same `custom_mul_n` interface. Karatsuba's base case is the same schoolbook code.
- **Verified:** every timed result in this dataset was first checked against GMP.

**Repeats and statistics.**
- Experiments 1–4 have 5 repeats; the fine-grained Karatsuba size sweep has 3.
- Every number reported is the median over repeats.
- Run-to-run spread, (max − min) / median, has a median of 11.8% across all cells. The worst cells are FFT at n = 6144 (130%) and schoolbook at n = 4096 (68%).
- So differences under about 15% at a single size should not be read as real.

**Inputs.** Uniformly random operands with the top bit set, so each has exactly n limbs. Karatsuba's operation count depends only on n; the data only affects carries and the sign branch. So random inputs are the right family for timing, and structured inputs were used for correctness instead (see below).

**End-to-end workload.** A chain of 20 modular squarings, x ← x² + 1 mod 2^(64n) − 1, timed over 5 chains.

**Things a careful reader should know.**
- **Uncontrolled hardware.** The benchmark ran on a laptop inside a VM. The process was pinned to one virtual CPU, but Windows decides which physical core (fast or efficient) runs that vCPU, and turbo frequency isn't controlled.
- **Background load matters.** An earlier attempt with other processes using about 5 cores ran 40–80% slower and was much noisier. That data was discarded, and the run here was made with the host otherwise idle.
- **Reproduce on dedicated hardware if possible.** Re-running on a desktop with native Ubuntu and a fixed CPU frequency would tighten the error bars.

**Distance from GMP.**
- Karatsuba is a constant **2.0× slower than GMP for n ≤ 64**. At those sizes both are effectively doing schoolbook, and Schoolbook is 1.93× slower than GMP at n = 8. So this factor is GMP's hand-written assembly inner loop against gcc's `__int128` C loop, not anything algorithmic.
- The gap then grows: 3.2× at 1024, 4.0× at 4096, 9.5× at 32,768 and 16× at 131,072 limbs. Over that range GMP moves on to Toom-Cook and then its own FFT, which grow more slowly than n^1.585.

**End to end vs isolated** (`Tables.md` §7).
- The time per squaring in the chain is within ±15% of the isolated multiply time at the same n for every algorithm, and the ranking is identical. The O(n) fold, increment and copy are negligible next to the multiplication.
- The outliers are the FFT at n ≤ 64 (21–24% faster in the chain). That's likely an artefact of the very short chains (about 0.2 ms each) rather than real; to use e2e numbers in the report, re-run with more iterations (e.g. `--iters 50`).

## Karatsuba specific findings

**1. The cutoff matters enormously, but the optimum is broad** (`Figures/threshold_sweep.png`, `Tables.md` §5).

Time relative to the best cutoff for each size (geometric mean of the six sizes):

| cutoff | 1 | 2 | 4 | 8 | 16 | 28 | 32 | 64 | 128 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| relative time | 5.18× | 2.35× | 1.41× | 1.07× | 1.02× | 1.01× | 1.08× | 1.30× | 1.56× |

- **Pure Karatsuba (recursing all the way to single limbs) is 4–6× slower than the tuned version.**
- **Every cutoff from 14 to 28 is within 3% of the best.** The default of 16 sits in that range.
- **For power-of-two sizes only the leaf size matters.** Every cutoff in [2^j, 2^(j+1) − 1] produces an identical recursion tree with 2^j-limb leaves, which is why the chart shows flat steps. Leaves of 16 are best; 8 costs 3–7% more and 32 costs 8–10% more.

**2. No strong sawtooth across recursion levels** (`Figures/karatsuba_sawtooth.png`, `Tables.md` §6).

Expected:
- Counting multiplications alone predicts a sawtooth.
- Just above n = 16·2^k the recursion gains a level and the leaves halve from 16 to about 8 limbs. That cuts leaf multiplications by about 25%, which should then grow back over the band.

Measured:
- One more limb past the boundary costs +15% at n = 65, +7% at 129, and only 0–2% from 256 up (e.g. 209 µs at n = 1024 vs 208 µs at 1025).
- Above 256 limbs, size-to-size wiggles are noise. The three repeats' curves are essentially uncorrelated (r = 0.03, 0.08, 0.35).

Explanation:
- For leaves of L limbs, leaf work scales as L^0.415 · n^1.585.
- The linear add/subtract work summed over all levels scales as L^−0.585 · n^1.585. It's dominated by the bottom levels, of which there are more when L is smaller.
- So halving the leaves saves multiplications but adds a level of linear work, and the two roughly cancel. This is the same reason the cutoff optimum above is flat.

**3. Time per n^1.585 creeps up about 35%, then levels off, exactly as the recursion depth predicts.**
- The mean of time / n^1.585 rises from 2.78 ns (17–32 limbs) to 3.42 ns (129–256), 3.55 ns (513–1024) and 3.68 ns (1025–2048). All three repeats agree.
- Why: with depth d, level i does linear work proportional to n·(3/2)^i. Summed over the levels, that's proportional to n^1.585 · (1 − (2/3)^d). So the linear work's share of the total only reaches its long-run value as d grows: 33% of it at d = 1, 80% at d = 4, 94% at d = 7.
- Fitting time / n^1.585 = A + B·(1 − (2/3)^d) to all 271 sizes gives A = 2.15 ns (leaf work) and B = 1.56 ns (work that grows with depth). The model matches the measured mean at each depth within 1.5% for d = 2–7 (+6% at d = 1, from only 3 sizes; +3% at d = 8).
- Implication (an estimate from this two-parameter model, not a profile): at large n, about 40% of Karatsuba's time is linear add/subtract/compare work and recursion overhead, not leaf multiplication. A profiler run would confirm the split.

## Things the data shows about the other algorithms

**The FFT's time is a staircase.**
- Within each band from 1.5·2^k to 2^(k+1) limbs its time is flat. For example: 53.7 vs 53.6 µs at 192 and 256 limbs; 326 vs 332 µs at 768 and 1024; 3.83 vs 3.72 ms at 3072 and 4096.
- The cause is that the transform length is rounded up to the next power of two (`FftMul.c:74-79`), so n = 1.5·2^k pays for 2^(k+1).
- Going from 2048 to 3072 limbs the time jumps 4.6×: above `SMALL_OPERAND_LIMBS = 2048` the digits shrink from 16 to 8 bits (`FftMul.c:68`), making the transform 4× longer.

**The FFT scales as about n^1.4, not n log n.**
- Between 4096 and 131,072 limbs (same position on each step) it grows as about n^1.40, where n log n predicts about n^1.08.
- Likely cause (untested): memory traffic. At 32K limbs the FFT's buffers (four double arrays, twiddle and bit-reversal tables) total 24 MiB, the size of the 24 MB L3. At 131K they're 96 MiB, well beyond it. The radix-2 loop also reads twiddles with a large stride.
- These three effects together are why Karatsuba holds off this FFT until about 100K limbs.

## Candidate surprises (for report section 5)

These are only surprises if they contradict what you wrote in section 2 before measuring. Check against your own predictions; don't adopt these wholesale.

1. **The asymptotically better algorithm loses for a very long time.** Karatsuba (n^1.585) beats our FFT (n log n) at every size up to about 64K–128K limbs, about 4–8 million bits. The reasons are concrete and measurable: power-of-two padding, the digit-size switch, and memory-bound scaling.
2. **Pure Karatsuba is 5× slower than hybrid Karatsuba.** All of its theoretical advantage over schoolbook is eaten by recursion and linear overhead unless the recursion stops at about 16 limbs.
3. **The recursion-level sawtooth that operation counting predicts doesn't appear.** Leaf work and per-level overhead move in opposite directions and cancel.
4. **Half of the gap to GMP at small sizes isn't algorithmic.** At n ≤ 64 GMP is 2× faster doing the same schoolbook algorithm, purely through its assembly inner loop.

## Correctness evidence (for the Karatsuba section)

- **Every benchmark run above verified its result against `mpn_mul_n` before timing:** 2,438 runs with zero mismatches (`Raw/errors.log` is empty). For Karatsuba this covers every n from 16 to 2112 in steps of 8, plus 16·2^k and 16·2^k + 1 for k up to 7, all main-grid sizes up to 131,072, and 18 different cutoffs.
- **Standalone structured-input test (2026-10-28): 51,055 checks against `mpn_mul_n`, 0 failures.**
  - Sizes: every n from 1 to 200, plus 255–257, 511–513, 1000, 1023–1025, 2047, 2049, 4095, 4097 and 10007.
  - Inputs: all ones (maximum carries), zero, one, top limb only, GMP's `mpn_random2` long-run generator, a0 > a1, a0 < a1, a0 = a1 (zero difference), and squaring with aliased operands.
  - Builds: cutoffs 1, 2, 3, 4, 8, 32 and 64 under AddressSanitizer and UndefinedBehaviorSanitizer, plus a normal `-O2` build at the default of 16.
  - Overruns: canary limbs past `result[2n − 1]` checked for writes past the end. Exact-size scratch, so ASan catches scratch overruns.
  - Monotonicity: one large setup reused for every smaller n, checking that the scratch size is monotone in n.
- **Mutation check:** two deliberately broken versions were both caught. Flipping the sign case tripped the `carry == 0` assert, and splitting at ⌊n/2⌋ instead of ⌈n/2⌉ produced mismatches.
- That test program isn't in the repository yet; it's at `KaratsubaTest.c` in Claude's session scratchpad. Add it to `Code/` if the report cites it.

## Notes for the AI-use section (Jack, from the Claude Code session)

Specific cases where the AI was wrong or misleading, and what was done about each:

1. **Guessed parameter presented as a default.** Claude first set `KARATSUBA_THRESHOLD` to 32 from general knowledge of GMP's thresholds. The sweep showed 32 is about 8% slower than the best cutoff (anything from 14 to 28 is within 3%), so it was changed to 16.
2. **Over-confident prediction, then an over-claiming chart.**
   - Claude's first briefing predicted Karatsuba time would be a sawtooth across recursion levels.
   - The first version of the figure was titled "Karatsuba time is not a smooth function of n".
   - Checking whether the three repeats agreed (correlation ≈ 0 above 256 limbs) showed most of that structure was noise. The title and summary were rewritten to claim only what replicates.
3. **Misleading test output.** When Claude deliberately broke the code to test the test, the first run printed `exit=0` with no output, which looked like the broken code passed. The exit code was `tail`'s, from a pipeline, and stderr had been hidden. Re-running with stderr showed the assertion firing.
4. **Wrong diagnosis of slow benchmarks.** The first full run was about 2× slower than earlier runs. Claude first blamed pinning to an efficiency core; a per-CPU speed check disproved that, and the real cause was other processes using about 5 cores. That data was discarded and the suite re-run on an idle host.
5. **Plausible but wrong explanation.** Claude's first draft of this summary put the 35% rise in time / n^1.585 down to cache effects. On checking, the rise starts at sizes whose working set fits easily in L1. An operation-count model with finite recursion depth explains it within 1.5% (Karatsuba finding 3), so the cache explanation was replaced.

Separately, the current report draft states Karatsuba is Θ(n^1.5) and writes the identity with a0a1 and b0b1. It should be Θ(n^log₂3) and (a0+a1)(b0+b1) − a0b0 − a1b1 = a0b1 + a1b0. If that text came from an AI tool, it's another example.
